# Phase 2 — private beta architecture plan

Assessment date: October 28, 2026. This is a plan, not implemented infrastructure. No accounts, credentials, subscriptions, cloud writes, OpenAlex/Unpaywall requests, or deployments were created in this pass. Costs below are current published starting points, not quotes or incurred charges.

## Recommended decision

Keep the current interface and local export/import. First finish beta entry gates, then implement invite-only authentication and owner-isolated persistence in a staging environment. Migrate only through an explicit preview-and-confirm flow. Add lawful full-text availability enrichment next; broaden discovery last. Do not combine an auth migration, storage migration, and discovery-provider change into one release.

## Minimal target architecture (future work only)

- Preserve anonymous discovery where permitted. Saving to the cloud is an optional explicit sign-in step; the private beta itself needs invite/allowlist checks on every page and API, not only hidden navigation.
- Use Supabase SSR cookie sessions with server verification, not an unverified client session. This application is Next.js 15: session-refresh interception belongs in middleware.ts, not Next.js 16's proxy.ts. Keep publishable keys scoped by RLS; never ship service-role keys to browsers. [SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client?queryGroups=framework&framework=nextjs).
- Suggested tables: assignments(id, owner_id, question, rubric_text, requirements, revision); sources(doi, metadata, provider, fetched_at); user_sources(owner_id, doi); assignment_sources(assignment_id, owner_id, doi); checklist_items(id, assignment_id, owner_id, text, complete, confirmed_at). Shared bibliographic metadata must never carry student rubrics or private annotations.
- Enforce owner_id = authenticated user ID for read/write/delete, including joining assignment_sources to an assignment of the same owner. Composite keys/FKs and RLS must prevent linking one student's source/checklist to another student's assignment. Test with two real staging users and anonymous requests before any migration. [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
- Add revision-based optimistic concurrency and transactions for assignment/checklist/source changes. Store an import idempotency key, canonical DOI and stable ID map; use explicit conflict copies, not last-write-wins. A browser Web Lock is only local coordination, not a cloud transaction.
- Initially store extracted rubric text, not original files, unless retention is explicitly chosen. If originals are needed, use a private bucket, short-lived signed URLs, owner checks, file type/size/decompression limits, retention and deletion jobs. Do not automatically copy licensed full texts or publisher PDFs into storage.
- Add provenance-bearing access evidence later: provider, DOI, evidence URL, license/version, fetched_at and expiry. Map verified lawful location -> free full-text link; explicit publisher evidence -> subscription label; absent/stale/conflicting evidence -> unknown. A journal DOI or OpenAlex index entry does not establish peer review. Credibility remains unassessed without a defined, audited editorial process.

## Safest implementation order and acceptance gates

1. **P0, approve beta scope and budget.** Confirm invite list size, device/browser support, student-data retention and recovery expectations. Review this PR and resolve launch blockers in QA_REPORT.md. No cloud service creation or spending yet.
2. **P0, host compatibility spike in staging.** Pick host/perimeter; resolve 10 MB vs 4.5 MB; verify Node 24, PDF worker/native packaging, TLS, response limits, memory/timeouts and request throttling. Confirm unauthorized page/API requests are rejected. Check previews and custom/production domains separately.
3. **P0, auth and isolation.** Add invite-only Supabase auth plus production SMTP. Test login/logout, link expiry/scanners, callback allowlists, refresh, account switching, anonymous access, and two-owner RLS boundaries. No student data migration yet.
4. **P0, transactional persistence with local fallback.** Add tables, revisions, rollback and restore tests, server validation, deletion policy, and export/import parity. Explicitly show local/cloud save state; never call a local write a cloud backup. Keep original local data untouched.
5. **P0, opt-in migration.** Export first; show assignment/source/checklist counts and conflicts; confirm account and destination; validate all records; transact; verify remote read-back; only then mark imported. Never clear localStorage automatically. Map legacy string IDs to UUIDs and deduplicate DOI variants. Test repeated import, interrupted import, full/quota failures, two devices, logout/account switch and rollback from a downloaded backup.
6. **P1, Unpaywall access enrichment.** Authorize a contact email later; add server adapter, TTL cache, bounded retry, request budget and per-provider failures. Preserve unknown states and original DOI links. Do not turn unavailable enrichment into invented free access.
7. **P1, optional OpenAlex expansion.** Only after provenance/conflict rules and budget controls pass. Add a free key through a separately authorized setup, leave paid credit purchasing off, define dedup/ranking, and compare topic relevance on the frozen corpus and live sampled queries. Keep Crossref available during rollback.
8. **P0 before student invitations, controlled release.** Test production-equivalent migrations and recovery with synthetic accounts, mobile browsers, constrained networking, accessibility and resource exhaustion; obtain an explicit deploy decision. Start with a small invite cohort and a support/recovery contact. Log errors/counters without student questions, rubrics, secrets or full article text.

## Migration hazards to test explicitly

Local work is tied to origin/browser/profile; a hostname change needs a user-initiated export/import. Multiple students can share one browser: never auto-associate pre-existing local work with the first account that signs in. Email address is not an owner ID. Metadata changes must not overwrite student's confirmed checklist work. Distinguish whole-library removal from unlinking one assignment. A successful HTTP response alone is not a verified backup; test restore/read-back. No school compliance, journal credibility, uptime or grade guarantee is implied by any provider plan.
